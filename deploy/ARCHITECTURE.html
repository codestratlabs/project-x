Company Evidence on AWS

Production architecture for the company evidence pipeline: an input file per company in S3 starts an Airflow run that downloads the company's SEC filings, extracts the evidence and publishes the findings workbook to the company's folder.

1Overview

The pipeline code is unchanged. Every folder it reads or writes is set through environment variables (PX_DATA, PX_DUMPS, PX_FINDER_ROOT, PX_WORK) or a command-line option (--formd-db, --employee-dir), so each Airflow task stages its inputs from S3 to local disk, runs the existing script, and writes its outputs back to S3. The production work is the container image, a task wrapper, the Airflow DAGs and the S3 and database locations.

Each company is independent: one input file, one DAG run, one set of S3 prefixes. Form D, N-PORT and DOL data are maintained once for all companies by their own ingestion jobs and read by the run. Two tasks call a language model: task 3, where the name finder sets aside look-alike names, and task 6, indirect mentions.

4Input specification

One file per company at input/<company>/company.json. The format is the configuration the pipeline already reads (pipeline/config/<company>.json), plus run_indirect, which only the task wrapper reads.

{
  "name": "Lungpacer",
  "company": {
    "legal_name": "Lungpacer Medical, Inc.",
    "aliases": ["Lungpacer", "AeroPace"],
    "description": "Medical device company in Exton, Pennsylvania …",
    "name_regex": "lungpacer",
    "cik": "0001708893",
    "employee_company": "Lungpacer Medical"
  },
  "k401_plan": "001",
  "run_indirect": true
}
FieldUsed for
name, company.aliasesSEC full-text search phrases (task 2) and the name finder's names (task 1)
company.legal_name, company.descriptionThe name finder's look-alike check: what the company is, so another organisation with a similar name can be told apart. Without a description the check judges from the name alone
company.name_regexWhat counts as a mention in the evidence and indirect tasks, and the issuer-name filter for N-PORT
company.cikThe company's own Form D notices
company.employee_companyThe company label on the DOL Form 5500 rows (required for the DOL sheet)
k401_planWhich DOL plan is the 401(k) plan
run_indirectWhether task 6 (model cost) runs

PrefixHolds
raw/Filings as downloaded, kept across runs; a new run downloads only filings not yet in the manifest. files/ is the pipeline's dump folder for the company, as is
intermediate/Files one task produces for the next: the name finder's mentions, structured records, evidence rows, the filings prepared for task 6 (copied, not linked, so another machine can read them) and indirect-mention decisions. Kept per run for audit and for re-running a single task
reports/The findings workbook per run; latest/ holds the newest
runs/Run record: inputs, task status, counts, model cost
reference/Shared, read-only: the Form D database file; each company's N-PORT holdings (or the N-PORT database on the worker's disk, 15 GB); the DOL Form 5500 rows labelled with company.employee_company

7Delivery plan

  1. Phase 1. Pipeline image, task wrapper and the company_evidence DAG. Acceptance: the Databricks workbook produced on AWS matches the current workbook cell for cell in every value; only text a language model writes (its reasons) may differ in wording, because model answers are not repeatable word for word.
  2. Phase 2. company_intake DAG, run records and failure alerts; Form D from the database and N-PORT from S3, moving to the N-PORT pipeline when it is released. Acceptance: Lungpacer and Horizon3 run from their input files alone.
  3. Phase 3. Evidence tables in a database, using the schema in the pipeline design document.
  4. Phase 4. Additional sources, one connector at a time: Form D of other issuers, loan terms, stated figures, H-1B, FPDS and USAspending, Companies House.
